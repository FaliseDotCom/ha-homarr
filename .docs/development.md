# Development

How the Homarr app is put together, and how to test a change before it reaches users.

## Repository layout

```text
repository.yaml              App repository definition, read by the Supervisor
homarr/
  config.yaml                App definition: version, port, options and schema
  Dockerfile                 Upstream Homarr image plus security updates, jq, tzdata and a health check
  run.sh                     Reads the options, prepares the environment, starts Homarr
  homarr-cli                 Runs Homarr's command line inside the running app
  DOCS.md                    User documentation, shown on the Documentation tab
  README.md                  Short description, shown in the app store
  CHANGELOG.md               Release notes, shown when an update is available
  icon.png, logo.png         Artwork, resized from Homarr's own logo
  translations/              Option names and descriptions (en, nl)
.devcontainer/, .vscode/     Home Assistant development environment
.docs/                       Documentation for contributors; security.md covers the image patches
.github/                     Dependabot and the workflow that completes its Homarr updates
scripts/update-homarr.sh     Bumps the app to a new Homarr release
```

## How the app works

The image extends the official
[`ghcr.io/homarr-labs/homarr`](https://github.com/homarr-labs/homarr/pkgs/container/homarr)
image, pinned to an exact release. That image is Alpine based and already runs everything
Homarr needs in one container: nginx on port 7575 in front of Next.js (port 3000) and its
WebSocket server (port 3001), an internal Redis, and SQLite in `/appdata/db/db.sqlite`.

On top of it, the Dockerfile upgrades the Alpine packages to their latest security fixes and
can swap in a newer Node.js; see [Security](security.md).

`run.sh` replaces the upstream entrypoint; Docker's `init` (enabled with `init: true`) runs it
as a child of a minimal init process, which forwards signals and reaps zombies. It:

1. Reads the options from `/appdata/options.json` with `jq`, and validates `base_url`.
2. Generates `SECRET_ENCRYPTION_KEY` on first start and keeps it in
   `/appdata/secret_encryption_key` (readable by root only). Homarr refuses to start without
   it, and needs the same key to decrypt the integration secrets in its database.
3. Exports Homarr's environment variables from the options, sets `ENABLE_DOCKER=false`, and
   finally exports the `env_vars` entries, which can override all of the above.
4. Saves those variables in `/run/homarr-app/console.env` for `homarr-cli`.
5. Replaces itself with the upstream `/app/entrypoint.sh sh run.sh`. Upstream's `run.sh` runs
   the database migrations, starts nginx, Redis and Next.js, restarts Next.js when it exits,
   and stops all three on `SIGTERM` or `SIGINT`. Redis saves its dump when it stops.

The Dockerfile defines a health check on `/api/health/live` through nginx. That endpoint
checks both the database and Redis, and nginx only starts after the migrations, so the
Supervisor shows the app as *starting* until Homarr is ready, and its watchdog restarts the
app when the check fails after the 5-minute start period. Homarr's request proxy skips
`/api` paths, so the check is not redirected to the onboarding page on a fresh install. The
upstream image has no health check of its own.

`timeout: 30` in `config.yaml` gives Redis and SQLite time to finish writing before Docker
kills the container.

The upstream image sets `DB_URL`, `DB_DIALECT`, `DB_DRIVER`, `AUTH_PROVIDERS` and `NODE_ENV`
with `ENV`, so `homarr-cli` sees those without `console.env`. `AUTH_SECRET` and
`HOMARR_REQUEST_IDENTITY_SECRET` are generated by upstream's `run.sh` on every start.

### Command line

`docker exec` starts a process that does not inherit `run.sh`'s environment, and Homarr's
command line validates `SECRET_ENCRYPTION_KEY` like the server does. `homarr-cli` loads the
settings that `run.sh` saved in `/run/homarr-app/console.env` (readable by root only) and runs
the upstream `/usr/bin/homarr` wrapper.

Upstream's command line keeps running after a command that opened the database, such as
`users list`, has printed its result; the same happens when `node ./cli.cjs` is run
directly, so it is not caused by the wrapper. `DOCS.md` tells users to press Ctrl+C.

### Storage

The upstream image declares `/appdata` as a `VOLUME`. `config.yaml` maps the app's data
folder there (`map: type: data, path: /appdata`), so the Supervisor's bind mount covers the
volume and Docker creates no anonymous volume, whose contents would be lost on the next
start and missing from backups. `options.json` moves along with it.

| Path in the container                 | Contents                                       | In backups |
| ------------------------------------- | ---------------------------------------------- | ---------- |
| `/appdata/db`                         | SQLite database: boards, users, integrations   | Yes        |
| `/appdata/redis`                      | Redis dump: caches and job state               | Yes        |
| `/appdata/trusted-certificates`       | Certificates trusted on Homarr's Certificates page | Yes    |
| `/appdata/secret_encryption_key`      | Key for the integration secrets in the database | Yes       |
| `/appdata/options.json`               | App options, written by the Supervisor         | Yes        |

`backup: cold` stops the app during a backup so the SQLite files are consistent.

### Design decisions

**Data folder at `/appdata`.** The alternatives were worse: linking `/appdata` to `/data`
fails because the image's `VOLUME` is mounted there, and copying the upstream filesystem
into a `FROM scratch` image to drop the `VOLUME` would mean repeating all of upstream's `ENV`
lines here. Moving the data mount keeps Homarr's own paths unchanged.

**No ingress.** Home Assistant's ingress serves an app under a per-session sub-path
(`/api/hassio_ingress/<token>/`). Homarr is a Next.js application whose base path is fixed
at build time, so it breaks under that prefix. The app publishes port 7575 and sets `webui`
instead, which gives the **Open web UI** button. `DOCS.md` explains how to add a sidebar entry
with a Webpage dashboard; Homarr's Content Security Policy allows framing
(`frame-ancestors *`) on all pages except its OAuth consent pages.

**No Docker access.** Homarr can manage containers through the Docker socket, but
`docker_api` gives an app control over the whole host and lowers its security rating to the
minimum. The app sets `ENABLE_DOCKER=false` instead; users who run a Docker socket proxy can
turn it back on with `env_vars` and `DOCKER_HOSTNAMES`.

**Generated encryption key.** A key in the options would be visible on the Configuration
tab and easy to lose or change by accident, which makes every stored integration secret
unreadable. Generating it once into the data folder keeps it out of sight and inside every
backup, next to the database it belongs to.

**`env_vars` as an escape hatch.** Homarr has dozens of environment variables, most of them
for OIDC and LDAP sign-in. Each one an option of its own would bloat the Configuration tab
for the few users who need them. Common settings get an option; everything else goes
through `env_vars`.

**Cold backups.** A hot backup of a live SQLite database can catch it halfway through a
write. Homarr restarts in seconds, so a short stop is the simpler and safer trade.

**Locally built image.** The Supervisor builds the Dockerfile on the user's device; there is
no `image` key in `config.yaml`. The build only adds two Alpine packages to the upstream
image, so it takes about as long as pulling that image.

**Upstream versioned tags.** `ghcr.io/homarr-labs/homarr:v<version>` is published for
`amd64` and `arm64`, which map to the Supervisor's `amd64` and `aarch64`.

## Testing a change

Work through these in order. Each catches problems the previous one cannot.

### 1. Lint

```bash
docker run --rm -v "$PWD:/mnt" koalaman/shellcheck:stable \
  /mnt/homarr/run.sh /mnt/homarr/homarr-cli /mnt/scripts/update-homarr.sh
```

After changing a workflow, check it with [actionlint](https://github.com/rhysd/actionlint):

```bash
docker run --rm -v "$PWD:/repo" -w /repo rhysd/actionlint:latest
```

### 2. Build and run with Docker

This checks the image and `run.sh` without Home Assistant. It needs Docker Desktop or any
Docker Engine.

```bash
docker build -t local/homarr-app homarr

mkdir -p test/data
cat > test/data/options.json <<'JSON'
{
  "log_level": "info",
  "no_external_connection": false,
  "env_vars": []
}
JSON

docker run --rm --init --name homarr-test -p 7575:7575 -e TZ=Europe/Amsterdam \
  -v "$PWD/test/data:/appdata" local/homarr-app
```

Open <http://localhost:7575> and complete the onboarding. Stop with `docker stop homarr-test`;
the log should end with `Shutdown complete.` The `test/` folder is ignored by Git.

To check the `aarch64` build on an `amd64` machine (slow, uses emulation):

```bash
docker buildx build --platform linux/arm64 -t local/homarr-app:arm64 homarr
```

Things worth checking after a change to `run.sh`:

- A fresh start creates `test/data/secret_encryption_key`, and a second start reuses it.
- `docker inspect --format '{{json .State.Health}}' homarr-test` turns `healthy` once Homarr
  is ready.
- `docker exec homarr-test timeout 30 homarr-cli users list` lists the administrator.
- An `env_vars` entry shows up in the log (`Setting NAME from env_vars.`) and in
  `docker exec homarr-test cat /run/homarr-app/console.env`.
- A `base_url` with a path stops the app with a clear message.

### 3. Run in a development Home Assistant

The repository includes the official Home Assistant development container, which runs a
complete Home Assistant with a Supervisor inside Docker. This tests the parts plain Docker
cannot: `config.yaml` with the `/appdata` data mount, the options form, translations, the
**Open web UI** button and the watchdog.

1. Install the VS Code *Dev Containers* extension and start Docker Desktop.
2. Open the repository in VS Code and select **Reopen in Container**.
3. Run the task **Start Home Assistant** (**Terminal** > **Run Task**).
4. Open <http://localhost:7123>, complete onboarding, and go to **Settings** > **Apps** >
   **Install app**. Homarr is listed under **Local apps**.

Port 7575 is forwarded from the development container, so **Open web UI** works from the
same computer.

### 4. Install on a real Home Assistant

1. Install the **Samba share** or **Advanced SSH & Web Terminal** app.
2. Copy the `homarr/` folder into the `local_apps` share (the `/addons` folder over SSH).
3. Go to **Settings** > **Apps** > **Install app**, open the three-dots menu and select
   **Check for updates**. Homarr appears under **Local apps**.
4. Install, configure and start it as described in `DOCS.md`.

A local copy is a separate app from the one installed from GitHub, with its own data, so
both can be installed side by side, as long as one of them gets another port. After changing
files, rebuild from the app's three-dots menu (**Rebuild**).
